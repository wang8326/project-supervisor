# {{PROJECT_NAME}} 更新治理规范（project-supervisor v3）

生效日期：{{DATE}}

用户当前明确要求及适用的全局/项目规则优先，本 Skill 补充；普通问答不套开发流程。

## 0. 角色硬隔离

- 此前已指定为监管/监督/supervisor 的当前窗口永久只读；“开始执行/开始更新”只允许其创建一个不同 ID 的独立 executor。初始明确 executor 保持其身份及不同监管 ID。普通任务仅读取、评估、借鉴或隐式加载 Skill 不自动变监管，也不据此新建锁、文档或任务；实际需要监管协作时按授权绑定，歧义不赋予既有监管写权限。
- supervisor 只运行 `status`、`doctor`、`check`、`audit` 等只读检查，不修改仓库、不运行执行态命令。
- 新项目 bootstrap、代码、测试、配置和治理文档修改都由 executor 完成。认领必须记录 `executor` 角色、不同的 supervisor/executor ID、实际 model/reasoning、风险和精确文件路径。
- v3 锁存于 Git common dir，跨 worktree 共享。`docs/ACTIVE_TASK.md` 是静态指针，不能手工认领或清锁。
- `status`/`doctor` 可只读识别任意后端；下文共享态 `check`/`audit` 及 v3 写命令只用于 `project-supervisor-shared`。`external-repository-guard` 使用仓库自己的占用/提交/验收命令，不套通用 v3 写命令或迁移。

## 1. 风险分级

- **R1**：文档、文案、单页面小样式和无业务影响的机械调整。
- **R2**：普通功能、UI、API、查询、状态、供应商适配和跨文件故障修复。
- **R3**：认证、权限、隐私、密钥、计费、数据库迁移、数据、备份、并发、更新与发布。

## 2. 模型路由

2026-10-08 本地默认策略（不是官方强制要求，未经独立 A/B 性能验证）：

| 工作 | 模型 | 推理 |
|---|---|---|
| 日常只读监管、排期、范围与普通验收判断 | `gpt-6.1-sol` | `high` |
| R3 实现、复杂根因、高风险最终审查 | `gpt-6-astra` | `high` |
| 范围明确的日常开发 | `gpt-6.1-sol` | `medium` |
| 低影响机械调整 | `gpt-6-luna` | `low` / `medium` |

不自动启用 Max/Ultra，不一律最大模型，也不按版本号大小排序能力。明确用户偏好优先，已有项目模型 pin 需单独授权的治理任务更新，个人 Skill 更新不能覆盖。派发前核对目标 host 的当前模型设置/能力；旧列表缺项不能证明不可用，无法核实则记未知。每个 executor 记录请求与实际可核实的 model/reasoning，自报事实不是运行时认证。指定模型不可用时先说明，再选择符合既有授权和风险的 fallback；没有合适选择才询问，不得悄悄替换。

官方依据：[模型说明](https://learn.chatgpt.com/docs/models)推荐 6.1 Sol 用于复杂 coding/agent 工作、Luna 用于明确重复任务，Astra 保留最强能力定位，5.6 系列在 rollout 期间仍可用；[6.1 Sol API 页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)列出 `low/medium/high/xhigh/max`；[模型选择指导](https://developers.openai.com/api/docs/guides/model-selection)要求结合质量、时间和成本选择。API 档位与 Codex host 能力分别核对；这里只更新任务路由，不改业务模型/API 参数或全局配置。

实际可用模型及项目限制：待首次盘点后填写。

## 3. 标准流程

1. supervisor 只读接管，定义一个任务、风险、可观察验收标准和精确文件范围。
2. 派发前核对可信项目 ID、host、repo/common dir 和预期目录；初始 prompt 明确 executor、监管 ID、目标及基线。监管核对创建返回归属，executor 写前自核实际 ID/目录/Git；标题和旧复制 ID 不作依据。仅目标/归属有歧义时先只读核对再内部续派，不给明确任务追加固定审批。项目不符保持只读重新路由；同一已验证任务恢复用原 ID，新任务用实际新 ID。首次按项目规则完整读取必要记忆，同任务未变只核对最新状态/Git/锁与相关差异，然后在首个编辑前认领。
3. 区分观察、假设、已证实根因；环境故障先搜索完整运行入口再冻结 allowlist。同根因所有受影响入口是一项任务，后发现遗漏也不得越界修改。已授权范围内完成常规决策，不追加重复审批。
4. 在锁 active 时完成验证、精确暂存、diff 检查和提交。
5. 原 executor 运行 `submit`，共享状态进入 `awaiting_acceptance` 且继续锁定所有 worktree。
6. supervisor 只读核对实际提交、diff、测试输出、风险和回退；退回则让原 executor `resume`。
7. 接受后由原 executor `finish`，写入完成回执并转 idle。不得先清锁再提交；v3 不使用 `release`。

修改前后用短的“保留/明确修改/明确移除”对照，未授权移除为空。默认保留相关功能、内容、字段、按钮和完整旅程；未经用户明确授权不删、隐藏、禁用、缩窄或静默降级。先检查共用代码实际调用者；安全/简化不授权删除高级流程、必要错误处理或有效测试。复用已有验收，不新造长审计文档；真实行为取舍缺授权才询问。

## 4. 项目验证命令

- 定向测试：待核实。
- 完整测试：待核实。
- 类型/静态检查：待核实。
- 浏览器/交互测试：待核实。
- 构建：待核实。
- 差异检查：`git diff --check`、`git diff --cached --check`、`project_supervisor.py check`。

未知命令不得猜测为已通过；先检查项目脚本和文档。失败、跳过、超时、未运行与剩余风险必须如实记录。

纯文档做内容、引用及 diff 检查；程序行为变动才补相关行为回归，保留项目明确门禁。R2 按受影响路径和项目要求验证，不照搬其他仓库全量门禁。最终代码稳定、已知待修问题关闭后才启动最终全量；出现必要修正时可停止能安全停止的无效检查，旧结果不能冒充最终。满足验收即完成，监管无依据不加独立全套复审。

验证配置到首个消费者及适用恢复路径；兼容故障按适用性覆盖 API 缺失与抛异常，异步问题覆盖实际事件次序。未覆盖入口标黄，不能作为完整验证或发布依据。非技术配置流程还应验收业务字段、主操作和操作成本，内部版本/hash/协议/检查尽量自动完成且保留安全、费用、回退约束及既有高级流程。通过后仅因新差异、失败或具体疑点补验；监管只读审查证据，不重跑整套测试。

## 5. 发布规则

发布必须是新的独立 executor 任务且获得明确授权。开始前确认稳定提交、干净工作区、备份、生产配置、数据目录、构建产物、安装目标和回退方法。普通代码测试不能替代发布验证。源码完成、离线包验证、服务器安装、业务验收各自报告证据；无真实认证远端通道时不创建虚假安装任务或索要无法执行的授权，同名本地目录不代表远端。

## 6. 交付格式

每次报告：状态、任务、风险、用户变化、修改范围、实际验证命令与结果、未执行检查、剩余风险、回退点、base/final commit 和 v3 receipt ID。

当前交接仅保留当前结论、唯一下一项、实际风险和证据引用，替换过期判断，历史留 Git/已有授权记录并保留审计意义，不为归档另造报告。估算和汇报分开实现、必要验收、打包、安装，以实际剩余工作为据，不编造工期。

## 7. 跨电脑迁移

Git 携带项目事实，不携带 common-dir 中的实时锁。独立 clone/电脑不共享互斥。源端必须验收完成且 idle；不复制活跃 SQLite/WAL。当前脚本 migrate 仅迁移旧版 v1/v2，不导入 clone 状态；v3 指针存在但数据库缺失时保持只读，安排独立、可审核的重建/迁移任务，不能直接 init、覆盖指针或假造空闲。迁移期间避免两个独立副本并行写入。
