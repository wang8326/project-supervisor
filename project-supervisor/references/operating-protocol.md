# 通用项目监管运行协议（v3）

## 1. 当前任务先绑定角色

角色按真实任务授权和既有身份确定。此前已指定为监管/监督/supervisor 的当前窗口整个生命周期永久只读；后续的“开始执行”“继续做”“更新项目”只授权它安排一个新的独立 executor。初始已指定 executor 且给出不同 supervisor ID 的任务保持执行身份。普通任务只是读取、评估、借鉴或隐式加载本 Skill，不会自动变监管，也不因此新建锁、治理文档或任务；实际需要监管协作时再按目的绑定。角色不明确不能擅自给既有监管窗口写权限。用户当前明确要求及适用的全局/项目规则优先，本 Skill 补充；普通问答不套开发流程。

supervisor 只做控制面工作：读取仓库和 Git、运行 `status`/`doctor`/`check`/`audit`、核实需求、定义风险与验收标准、创建或继续一个独立执行任务、等待结果、检查提交和决定接受或退回。它不运行任何写命令，不编辑代码、测试、配置或治理文档，不构建、打包、安装、提交、发布或调用真实服务。

独立 executor 必须是另一个 Codex project task/thread，task ID 与 supervisor ID 不同。允许使用 linked worktree，因为 v3 锁位于 Git common dir。若当前环境不能创建独立任务，supervisor 停止并给出可复制的 executor 指令；不得在当前监管任务中执行，也不得用当前会话内 subagent 代替独立任务。

派发前核对可信项目 ID、目标 host、仓库/common dir 和预期工作目录；初始 prompt 明确 executor 身份、监管 ID、实际目标和基线。监管核对创建结果的实际归属，executor 始终在写入前自核运行时可见的实际任务 ID、真实目录和 Git；不能用标题或复制的旧 ID 代替。仅路由/归属有歧义时，初始 prompt 明确只读核对，待监管核实返回证据再发送执行指令；这是内部协调，不向用户重复审批，也不为归属明确的任务增加固定放行阶段。创建后的检查不能自动阻止一个已获写入指令并启动的任务。项目不符保持只读并重新路由；恢复已验证的同一任务用原 ID，新任务用实际新 ID。运行时未提供认证身份时，自报 ID 仍有第 5 节所述限制。

维护本 Skill 也遵守上述角色隔离；调用 skill-creator 不赋予 supervisor 写入身份。非仓库安装目录的维护见第 9 节。

## 2. 只读接管与后端识别

首次真实接管按项目规则完整读取必要的 `AGENTS.md`、产品简报、项目状态、更新治理、监管交接、静态状态指针和待办池，再检查 Git 状态、最新提交及相关差异。同一任务资料和规则未变，不重复全量读取，只核对最新状态、Git/锁及相关变化。只读 `status`/`doctor` 适用于识别任何后端；共享态 `check`/`audit` 要求共享后端：

- `project-supervisor-shared`：v3 共享 SQLite 状态可用；所有 worktree 共用一个事务锁与审计事件流。
- `legacy-project-supervisor`：识别到 v1/v2；只有空闲、干净状态可由独立 executor 显式 `migrate`。
- `external-repository-guard`：只有完整中文字段签名才识别为仓库自有守卫；遵循仓库自己的占用、提交和验收命令，不套通用 v3 写命令、不接管、不迁移或改写守卫。
- `missing` / `invalid`：报告缺失、损坏或指针不一致，不隐式修复。

`docs/ACTIVE_TASK.md` 在 v3 中只是受 Git 跟踪的静态指针。实时状态位于 `<git-common-dir>/project-supervisor/state-v3.sqlite3`，不提交到 Git。状态行与最后审计事件必须一致，写操作使用 SQLite 事务串行化。

以下 v3 初始化、认领、提交和完成命令只适用于共享后端；缺失后端的新项目须先按第 3 节显式初始化。

## 3. 新项目初始化

supervisor 先只读检查项目类型、已有说明、Git、验证命令、生产方式、敏感边界和现有改动，然后创建 bootstrap executor。监管任务不得自己运行 `init`。

bootstrap executor 在首个仓库写入前运行 `init --role executor ...`。脚本先在共享数据库建立 active 锁，再以不覆盖方式创建七份治理文件；任一目标已存在时整体停止。executor 将模板中的未知项替换成有证据的事实，保持锁 active，暂存且提交这些精确文件，运行验证，然后 `submit`。supervisor 只读验收后，原 executor 才能 `finish`。

初始化失败会清理已创建文件并记录 `init-aborted`；确认目标文件仍不存在后，同一流程可以重试。不得靠手工编辑静态指针伪造空闲或完成。

## 4. 普通执行任务与共享锁

一次只允许一个仓库修改任务。executor 在首个修改前声明一个任务、R1/R2/R3 风险、实际 model/reasoning、精确文件 allowlist 和必要的额外 `--protect` 路径，再运行 `claim`。

默认保留相关功能、内容、字段、按钮与完整操作旅程；未经用户明确授权不删除、隐藏、禁用、缩窄或静默降级。安全或简化本身不是删功能授权。修改共用代码先检查实际调用者；修改前后用短的“保留/明确修改/明确移除”对照，未授权移除为空。复用已有验收/有效测试，不新造长审计文档；只在真实行为取舍缺授权时询问。高级流程、必要错误处理和有效测试不能因极简被删。

允许范围必须是精确仓库相对文件。拒绝目录、仓库根、绝对路径、`..`、glob、`.git` 内部路径、符号链接路径、NTFS ADS，以及普通任务对 `docs/ACTIVE_TASK.md` 的修改。不要把 `src/`、`docs/` 或整个仓库作为范围。

认领会保存：起始提交、executor worktree、允许文件、所有既有 dirty/untracked 文件的状态与内容指纹、常见敏感文件、显式保护路径，以及 Git config/hooks/worktree 指针。认领前存在 staged 文件时停止。活动检查同时检查工作区和 `base_commit..HEAD`，因此把范围外文件提交掉也不能绕过守卫；新建被 Git 忽略的 `.env.*` 也会被发现。

executor 在锁 active 时完成实现、验证、精确暂存和提交。不得先清锁再提交。提交后运行 `submit`，状态变为 `awaiting_acceptance`，锁继续阻止其他 worktree 认领。此时代码和 HEAD 必须保持不变。

若 supervisor 退回，原 executor 运行 `resume --reason ...` 后继续；不能直接重复 `submit`。若任务放弃，只有工作区恢复基线且 HEAD 回到起始提交后，原 executor 才能 `abort`。脚本不会自动回退、删除或覆盖用户内容。

## 5. 验收与完成

supervisor 至少核对：

- 当前状态是 `awaiting_acceptance`，executor/task ID 与被派任务一致；
- `base_commit..final_commit` 仅含精确 allowlist；
- 工作区无任务残留，受保护路径和 Git 控制未变化；
- 实际 diff 满足可观察验收标准，没有夹带重构；
- 每条验证确实运行，失败、跳过、超时与未运行项均被如实报告；
- 安全、费用、数据、兼容与回退边界保持；
- 状态/交接文档只在事实实质变化时更新。

接受后，supervisor 把明确的接受结论发给原 executor。原 executor 运行 `finish --accepted-by <supervisor-id>`；脚本再次验证 HEAD、范围和保护项，写入不可变审计事件与完成回执，再转为 idle。`release` 已移除。

SQLite 提供协作互斥和普通完整性检查，不是防恶意参与者的安全边界。运行时若不提供认证身份，task ID、模型、验证文字和 `accepted-by` 仍是自报字段，所以人工/模型验收必须核对真实任务与证据。

## 6. 风险、验证与发布

- **R1**：文档、文案、小样式和无业务影响的机械调整；纯文档检查内容、引用和 diff，其余按实际影响验证。
- **R2**：普通功能、UI、API、查询、状态和跨文件故障；按受影响路径运行相关行为回归及项目明确要求的门禁，不把某个维护仓库的全量测试强加给所有项目。
- **R3**：认证、权限、隐私、密钥、计费、迁移、数据、备份、并发和发布；使用项目规定的高可靠性模型/推理，覆盖失败、越权、重复、兼容、回退与脱敏。

模型按 [model-routing.md](model-routing.md) 的日期化本地默认与项目/用户约束选择；每个 executor 重新确认实际模型。行为变化补回归测试，不用源码字符串断言代替用户行为。未经授权不调用付费或生产服务，不删除数据或轮换凭证。

保留项目明确要求的检查。只有最终代码稳定且已知待修问题关闭后，才启动最终全量门禁；启动后出现必要修正，可停止能安全停止的无效检查，旧结果不能冒充最终结果。已通过后只因相关差异、失败或具体疑点补验，验收满足即完成；监管只读审证据，无依据不增加独立全套复审。

故障、配置与交付判断读取 [diagnosis-and-delivery.md](diagnosis-and-delivery.md)：证据分级，完整运行入口搜索后定范围，验证首个消费者与恢复路径，未覆盖入口标黄。已有授权内自行完成常规决策，不反复询问；只读监管身份不因此改变。监管只检查已有验证证据，不重跑整套检查；有新差异、失败或缺口时再派补验。

发布永远是新的独立 executor 任务并需明确授权。开始前确认稳定提交、干净工作区、备份、生产配置、数据目录、构建产物、安装目标和回退；普通代码测试不能替代发布验证。分别记录源码、离线包、服务器安装与业务验收；本地同名路径不能代表远端。没有实际认证远程通道时不创建安装任务或索要无意义授权，交付已授权的本地结果并等待远端证据。

## 7. 治理文档与窗口轮换

supervisor 可以决定待办顺序和应更新的事实，但治理文档本身也只能由 executor 在声明范围内修改。交接保持短的当前结论、唯一下一任务、实际风险与证据引用；更新时替换已失效的当前判断，不逐轮叠加旧“唯一下一项”或整套测试历史。历史保存在 Git、v3 audit 或用户已授权的记录任务，不为归档新造报告，不为精简篡改过去事实或丢失审计意义，也不未经授权向其他任务/服务发送记录。估算与汇报分开实现、必要验收、打包和安装，以实际剩余工作为据，不编造工期。

完成发布、发生 R3 事故、模型或产品方向变化，或监管任务开始遗忘规则、混淆状态、重复分析时，先安排 executor 更新交接，再开启新的只读监管任务。新监管任务仍须重新接管。

## 8. 跨电脑与独立 clone 迁移

项目事实与模板随 Git，实时 SQLite 锁和审计状态位于 common dir，不随普通 clone。互斥仅覆盖共享该 common dir 的 linked worktree，不覆盖独立 clone、其他电脑或安装目录；不得声称分布式互斥。

迁移前由监管确认所有执行已结束、验收完成且状态 idle，核对干净提交与受保护文件。独立 executor 在明确范围内保存所需审计/回执证据，并按经过验证的迁移方案重建或显式迁移目标协调状态。不要复制活跃 SQLite/WAL，不把 active 或 awaiting_acceptance 强行改成 idle。

当前脚本的 `migrate` 仅支持符合条件的旧版 v1/v2 到 v3，不是跨 clone 导入命令。已跟踪 v3 指针但缺数据库的 clone 会报 invalid，不能直接 `init`（七文件已存在）、伪造旧状态或覆盖指针；保持只读，安排单独、可审核的状态重建/迁移实现与验证后才允许目标 executor 认领。先用只读 status/doctor 探测；失败的 claim 也可能创建空数据库文件，文件存在不代表有效实时状态。迁移期间不要让两个独立副本并行写入同一项目。

## 9. 非仓库个人 Skill 的外部维护

安装目录没有 Git/治理时，不假装它是已初始化项目，也不在安装目录 `git init` 或把业务仓库治理套进去。优先复用经核对基线、干净且空闲的既有维护副本，并确认其完整文件清单/字节与当前安装一致。独立 executor 在本次任务的隔离目录保存新的原始字节备份和完整哈希清单，再 claim 精确 Skill 路径；不重复 init 或重建根治理。没有合适副本时才建立版本化副本并只为它初始化 v3：bootstrap 只提交七份治理文件，经监管接受并 finish 后，另行 claim 修改 Skill。副本根治理仅描述外部维护边界，不回写安装目录。

所有修改和测试先在副本完成，保留可审查 diff、提交、验证结果和回退路径。回写前对安装目录原始清单及新增目标检查漂移；发生他人改动即停止回写并报告冲突。只回写明确修改文件，再核对安装结果与验证副本哈希一致，并保留安装前后清单。共享锁只保护副本，哈希核对也不是安装目录的跨进程事务锁；发现竞争或不一致不得报告成功。完成后 submit，收到监管明确接受才 finish。已获授权的个人 Skill 回写属于维护任务，不自动扩大为生产发布。
