# 诊断与交付判断

用于故障、环境兼容、管理员配置与发布状态判断；按项目实际入口应用，不预设技术栈。

## 先区分证据，再确定范围

- **观察事实**：用户在什么环境做了什么、看到什么；保留时间、入口与可复现条件。
- **假设**：可能原因及能区分它们的下一项检查。数量偏少、预览成功或 UI 提示本身不能证明上游权限、配置或响应内容。
- **已证实根因**：实际代码、脱敏上游证据或可复现测试支持的因果结论，并注明证据适用环境。离线夹具证明代码行为，不等于实测生产上游。

没有证据时不要要求用户反复改配置，也不要断言“无需改代码”。需要更多信息时，先完成已授权的只读证据收集，说明仍缺哪项证据及其会改变什么决策。

环境、平台或能力故障在冻结 allowlist 前，搜索完整受影响运行代码：失败 API、等价直接调用、共享封装、默认参数表达式及下游消费者。将命中归为受影响、已被安全封装覆盖、仅服务端或仅测试，并保存搜索范围/模式及剩余直接调用的解释。同一根因的所有受影响入口是一个连贯任务；不只修最先报错的按钮，也不扩展为无关重构。

认领后才发现遗漏路径时，不越过现有精确 allowlist。先记录覆盖缺口，由监管明确安排符合守卫的后续范围；原范围的交付标黄，不能宣称根因已全部闭环。不要为扩范围伪造验收或清锁。

修改共用代码前检查实际调用者，默认保留相关功能、内容、字段、按钮及完整旅程。修改前后用短的“保留/明确修改/明确移除”对照核实范围，未授权移除为空；不额外生成长审计文档。未经用户明确授权，不删除、隐藏、禁用、缩窄或静默降级能力；安全、简化或极简不能替代该授权，也不能成为删除高级流程、必要错误处理或有效测试的理由。仅对真实行为取舍缺少授权的部分询问。

## 验证用户旅程

配置成功应继续验证首个实际消费者动作，以及适用的失败、重试或恢复路径。交互测试在目标环境条件下执行；兼容故障在合理适用时分别覆盖 API 不存在与 API 存在但抛异常。流式/异步流程覆盖实际出错的事件次序，而非仅理想响应。

按入口列出实际覆盖与缺口；未测试的受影响入口标黄，阻止把交付称为完全验证或据此打包发布。用夹具和模拟避免未授权真实调用，明确它们与线上业务验收的差距。源码字符串检查、内部状态机通过或单一配置成功均不能代替用户可观察行为。

若项目面向非技术管理员，在新建或已授权调整的流程中优先呈现必要业务字段和一个“保存并启用”主动作；内部版本、hash、协议、校验与回退尽量由程序自动管理。这不授权删藏既有字段、按钮或高级流程；保留其完整可达性，不叠加新的强制配置流程。保留安全与费用约束，失败时给出可理解的原因并保留上次可用配置。复用既有验收，核对字段/操作成本和首个用户消费结果。

## 不把流程变成额外阻碍

在用户已授权范围内完成常规技术决策与必要工作，不为重复确认、可逆小步骤或推测风险增加审批。只对缺失且确实影响产品、成本、权限、数据或发布边界的决定请求输入；说明具体原因。用户中途提问或纠正时吸收新信息并继续原目标。自主推进始终受永久只读监管和独立执行的角色边界约束。

验证与实际改动相称：纯文档核对内容、引用和 diff；程序行为变化才补相关行为回归，优先复用有效测试，并保留项目明确门禁。最终代码稳定、已知待修问题关闭后才启动最终全量；运行中出现必要修正，可停止能安全停止的无效检查，旧结果不得冒充最终结果。通过后仅对新差异、失败或具体疑点补验，满足验收即完成。监管只读检查真实 diff/日志/提交，无依据不另起独立全套复审；必要补验续派原 executor 或符合项目规则的验证任务。

## 区分交付阶段

分别报告源码完成、离线包验证、服务器安装和用户业务验收；每项标明证据所在环境与尚未验证的内容。本地与远端同名路径仍是不同文件系统。

估算与进度汇报分开实现、必要验收、打包和安装，依据实际剩余工作说明，不把实现完成当作全部交付，也不编造工期。

没有真实、已认证且在授权范围内的远端通道时，不创建虚假生产安装任务，也不询问无法执行的“安装授权”。完成已授权的本地交付，提供适用的交付物和现有安装说明，等待负责人回传实际远端证据；不要为了填写状态而制作用户未请求的包。发布/安装授权不能从普通开发任务推断。
